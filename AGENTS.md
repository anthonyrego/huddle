# huddle: notes for coding agents

huddle is meeting software for macOS: people meet with voice (camera and screen share come later), and an AI whiteboard draws on a board everyone shares, but only when someone asks it to ("whiteboard, diagram what we just discussed, alphabetically"). It can also diagram and take notes as the meeting goes, on request, and it answers aloud when someone asks it a direct question. Only the AI writes to the board; every change is a version on the meeting's timeline.

Two binaries: `huddle`, the app (Go on SDL3 through `github.com/Zyko0/go-sdl3`, purego, no cgo, with our own GPU renderer), and `huddled`, the server (HTTP and a meeting WebSocket over Postgres; LiveKit carries the media). The engine is copied from an earlier project of the author's; per-file provenance lines say so.

## Rules
- **This repo is public (MIT).** No personal details in files or commit messages: names, emails, machines, hardware names, certificate hashes, team IDs, private repository names. Code copied from the author's private projects says "Copied from an earlier project of the author's"; code from reel (public) may name it. `SIGN`, `NOTARY_*` live in `local.mk`, which git ignores. Scan the diff and the history before every push. Push only when the user says.
- **The API key is never printed, logged or committed.** It comes from `GEMINI_API_KEY`; the Makefile takes only that line from `HUDDLE_ENV` (default `.env`, which git ignores; `.env.example` shows the line).
- **Don't open the user's microphone or capture their screen from an agent.** `make run` and the app joined to a room with voice on are the user's to run. Agents use fixtures, file-to-file runs, `render`, and `audio-devices` (lists devices, opens only the speakers).
- **Never touch the user's real data.** Dev runs set `HUDDLE_DATA_DIR` to `.dev/data` (the Makefile does).
- **No cgo.** Native code is loaded with purego only; builds use `CGO_ENABLED=0` and `make nocgo` checks the binaries build that way. Never import `github.com/livekit/server-sdk-go/v2/pkg/media` (it pulls libopus through cgo).
- **Agents' window runs use `-no-voice`.** It joins the room's audio listen-only: the speakers alone, the input node never touched. `audio-devices` opens only the speakers too, and says whether any process had the mic's device running. Voice on (the default) is the user's run. To check device choice, agents point the speakers at a virtual output (`audio-devices -speakers`, `TestSwitchSpeakers`, or a `devices.json` in a data dir of their own: never the user's `.dev/data`, which `make run` reads). They use `-no-video` too: the camera and the share are never opened (others' videos still come in and decode). `-fake-camera` makes the Camera and Share buttons send the test pattern instead.
- **Every call into the transpiled libopus goes through `opus.onPinned`.** The transpiled code passes Go stack addresses as uintptrs; a call that grows a moved stack reads garbage (an abort in SILK after concealment, only with the GC running). The pinned worker's stack is grown once and never shrinks. `TestConcealUnderGC` is the regression test. Under `-race`, Go's checkptr trips inside the transpiled code: race-test with `go test -race -gcflags=all=-d=checkptr=0`.
- **Go stays off the real-time audio thread.** AVAudioEngine taps and player completions run on the engine's own threads and only copy and signal. No AVAudioSinkNode or render callbacks from Go.
- **The core stays pure.** Everything under `internal/` except `gfx` and `platform` never imports SDL; `internal/deps/purity_test.go` enforces this; add new pure packages to its list.
- **Only the main thread touches the GPU.** Other goroutines write shared state under a lock and call `platform.Wake()` (see `meeting.update`).
- **Only the server changes the board.** Apps send commands and render versions; a version carries its layout (`wire.BoardVersion.Layout`, a `layout.Placement`), so every app and every replay draws the same picture.
- **The board is measured with the embedded fonts only** (`internal/board/measure`). A character Inter lacks draws as its missing-glyph box on the board rather than in a system face, because a system face would size differently on another machine. Text outside the board (the status pill, the field, the transcript) keeps the system fallback. A change to `measure` (or a card's geometry) changes every size the server places: an app drawing an older server's placement with newer measurements draws cards that don't fit their boxes, so the server and the apps ship such a change together.
- **Nothing reaches the brain without the gate.** Every turn starts from a gate command (wake, typed, key) or auto mode, which a command turned on; `agent-check` counts versions written without one (must be 0).
- **Answer drawing SILENT, speak and reads WHEN_IDLE** (see "What the models do"). Changing the scheduling, the tool descriptions or the system prompt (`internal/server/agent/prompt.go`) changes how the model behaves: run `agent-check` after.
- **Gemini spend is logged.** `agent-check` prints an estimate per run and appends it to `.dev/check/spend.log`. Fixture runs are short on purpose (about $0.03 each); the hour-long soak costs well under a dollar; run it when the reconnect or rotation code changes.
- **Migrations are append-only.** Never edit a migration that has run anywhere; add the next number.
- **The dev server is for a private network.** `huddled serve` refuses to run without `HUDDLE_DEV=1` until signing in exists (stage 3): anyone who reaches it can join any room.
- **Graphics shaders use no storage buffers.** After editing `shaders/src`, run `make shaders` and commit the outputs and `manifest.json`.
- **Colors come from `theme.Palette`.** Sizes are logical units.
- **Exit checks are run, not asserted.** Look at what you built: render it and read the PNG, run it against the local stack and read the log.
- **Copied code** keeps its one-line provenance comment. Code adapted from LiveKit (Apache 2.0: the media server's work, `internal/server/sfu` and `internal/rtc/sfuclient`) keeps LiveKit's copyright and license header, then one line naming the file and version it comes from and what changed; `NOTICE` and `LICENSES/Apache-2.0.txt` cover it, and the app carries both.

## Voice (Track V)
**The path.** Mic → voice processing (AVAudioEngine; the tap delivers 100 ms at a time, released 10 ms a frame) → Opus (20 ms, FEC, DTX) → lksdk sample track with the RFC 6464 level → LiveKit → each listener: raw RTP → (optional `Sim` interceptor) → jitter buffer → playout mix (10 ms, paced by the speaker) → AVAudioPlayerNode (50 ms queued) → speakers, where voice processing hears it and cancels it from the mic.

**Decisions, and why.**
- **Opus: libopus transpiled to Go (`kazzmir/opus-go`).** pion/opus has no public encoder (its CELT encoder is internal), so encoding had to be libopus either way; for decoding, the measurements below favour libopus too: real concealment and in-band FEC, where pion has neither (ours repeats the last frame, fading). Speech fixture, on the development Mac, `go test ./internal/opus -bench . -run Concealment -v`:

  | | libopus | pion |
  |---|---|---|
  | encode, 20 ms frame (complexity 9) | 0.48 ms (2.4% of a core; 1.3% at complexity 5) | no encoder |
  | decode, 20 ms frame | 44 µs (0.22%) | 55 µs (0.28%) |
  | conceal, 20 ms | 41 µs | 1 µs (repeat-fade) |
  | correlation with the source, 5% loss | 0.913 with FEC, 0.881 PLC only | 0.843 |
  | same, 10% loss | 0.909 with FEC, 0.848 PLC only | 0.762 |
  | lost frames vs the clean decode, 10% | 0.937 with FEC, 0.647 PLC only | -0.10 |

  The transpiled code's moving-stack bug (Rules) is contained by the pinned worker; `opus.Chosen` switches the decoder to pion in one line if it ever bites again.
- **lksdk takes our own pion interceptors**: `lksdk.WithInterceptors(...)`, and `WithIncludeDefaultInterceptors(true)` keeps its own (NACK, RTCP reports, TWCC, the RTT ones), which giving any custom list otherwise drops. Ours go in first, nearest the network, so everything after (RTCP receiver reports, the jitter buffer) sees what they do. The receive-side network simulation is one. lksdk also registers the RFC 6464 audio-level extension for audio itself; we write the level on every packet through `SampleWriteOptions.AudioLevel` (lksdk's `LocalTrack` can; pion's `TrackLocalStaticSample` can't), and the SFU's active-speaker levels show it arrives (`sfuSpeakerLevel` in `voice: track`).
- **Voice processing stays on AVAudioEngine with Go off the real-time thread**, so the mic comes from a tap, and taps come 100 ms at a time on this hardware whatever is asked (4800 frames every 100 ms in the earlier project's logs). Sent as bursts, those look like 80 ms of jitter to every receiver; `paced` releases them evenly instead, which costs nothing the chunking hasn't already (~90 ms on the mic side). That is the largest single latency in the path; lower would need native code on the render thread (an AVAudioSinkNode block or a render callback), which purego can only give us as Go.
- **Every voice's RTP timestamp follows the clock, sent or not** (a mic through DTX and mute, the whiteboard between answers), and **the jitter buffer starts its target over after a second with no packets.** LiveKit pads a track nobody has sent on yet: a new subscriber gets 251 frames of 80 bytes over 5.4 s whose timestamps step 961 samples every ~21.8 ms, slower than they arrive. That drift alone sets the target to 300 ms, and the 250-arrival window used to keep it there until 250 real packets had come (minutes of the whiteboard's answers); a timestamp that stood still through a silence did the same on every answer. Measured with a recorder in the room (`huddle voice -out`): the whiteboard's answers went from 300 ms to 40 ms. A mic's DTX frame every 400 ms keeps the window, so jitter learned before a pause carries across it (`TestPaddingThenSpeech`).
- **Voice processing doesn't start on every device, so the mic falls back to running without it.** On a USB interface that is both the default mic and speakers (2 in, 2 out, 44.1 kHz) the engine failed to start with `bfmt` (1650879860) in five of six runs of the earlier project and in huddle's first; each failure read the input node's device side as 0 Hz / 0 channels after voice processing was turned on, and the one start that came up read 44.1 kHz / 4 channels there. So start now waits for that format (up to 2 s), `OpenVoice` tries a second engine, and the call then opens the mic without echo cancelling (`NoEchoCancel`, the bar says "use headphones") rather than leaving the person listening only. Whether the wait or the second engine is enough on that interface is the user's run to tell (`audio: voice processing's device is ready`, `audio: the engine didn't start`). The menu's "Echo cancelling: Off" is for headphones.
- **The whiteboard's track sends a silent frame every 400 ms between answers** (`keepAlive` in `internal/server/agent/voice.go`), as a mic sends DTX. LiveKit pads only a track that hasn't sent: before this, an answer that began inside the padding played late, because the padding's arrivals were still in the window. Traced with `huddle voice -arrivals`: the padding's transit climbs about 1 ms a packet (−21 to +96 ms over 1.6 s), then the answer's sits flat at −8 ms, and that answer played at 119 ms (300 ms once, 4 s in). With the keepalive, the padding stops after about 15 frames, and an answer typed 1.5 s after joining plays at 41 ms. Keepalive frames are 17 bytes and decode to silence; the receiver counts the quiet between them as `skippedMs`, as it does a mic's DTX.
- **The speakers are paced by the player's completions** (`DataRendered`), 10 ms per buffer, 40–50 ms queued; Write gives up waiting after 200 ms and drops past 500 ms queued, so a stopped engine never stalls the mix (the watchdog restarts it).

**The user's gate.** Postgres and LiveKit running (`make dev-up`, `make livekit`); `scripts/voice-fixtures.sh` once for the fixtures. Logs: `.dev/data/logs/app.log` for `make run`; `~/Library/Logs/Huddle/app.log` for the app opened on its own.

## Video (stage 2)
- **Status, step 0, 2026-10-28:** the probe passed (below).
- **Status, Track P (the pipeline), 2026-10-28:** built on branch `track/p-pipeline`, merged on main: capture (the camera, the screen through the system picker, the pattern), a sender with an encoder per simulcast layer, LiveKit video both ways with congestion control and lip sync, the app's Camera and Share calls, `huddle video`, `huddled bot cam`, the whiteboard on voices only. Checked (below, "Track P's numbers"): `make check`; `GOOS=linux go vet ./...`; the `huddle video` loopbacks through LiveKit with the server on its own port; `TestAudioOnly` against LiveKit; an app run (`-no-voice -no-video`) receiving and decoding two `bot cam`s. Never run by an agent: a real camera, the permission prompt, the screen picker, a real screen (the user's gate, below).
- **The path.** Capture (camera, share or pattern: an NV12 `macvideo.Buffer` each frame, the capture's own memory) → `macvideo.Sender` (an encoder per layer, each handed the full picture: VideoToolbox scales it) → `room` (a simulcast track; GCC, the allocator and our pacer decide which layers run at what rate) → LiveKit (each receiver gets the layer its `SetSize` fits) → `room` again (assembler → held for lip sync → decoder → newer than the last shown → `video.Latest`) → the window takes the newest frame (Track U's tiles).
- **Layers.** A camera: its picture at up to 1280 wide (1.7 Mbps at 720p), half (450 kbps at 360p) and a quarter (160 kbps at 180p), all at 30 fps. A screen: up to 1920 wide (2.5 Mbps at 1080p) and half (800 kbps), at up to 15 fps. A layer runs from 40% of its bitrate (its floor) to all of it. Keyframes every 5 s at most, and whenever a receiver asks (once per 200 ms per layer).
- **Congestion control.** pion's GCC (`cc` + `gcc.NewSendSideBWE`, with `twcc.NewHeaderExtensionInterceptor`, which lksdk doesn't add for what it sends) gives an estimate; the publisher connection's estimator is matched by `GetPublisherPeerConnection().ID()`.
  - **pion's GCC climbs while less is sent than it allows** (8% a second, to its maximum: it has no cap at the acknowledged rate as WebRTC's has), so the layers are given at most 1.5× what was sent plus 100 kbps ("usable" in the logs). `huddle video` prints both.
  - **A paused layer comes back through a probe:** the highest running layer is given the paused layer's floor on top, rising over 8 s (4 s while the estimate has never dropped), and pads what its encoder doesn't use with SEI filler payloads (NAL 6, message 3; pion's payloader drops filler-data NAL units, type 12). If GCC drops meanwhile, the probe ends at once and the layer waits 15 s, doubling to 2 minutes; if it carries the floor, the layer starts at its floor. Probing with the paused layer itself was tried first: the SFU switched receivers up to it and back, with keyframes both ways and the voice's jitter delay at 260 ms. Probes wait for 10 s with no drop of 15% or more in GCC's estimate.
  - **A running layer pauses under 70% of its floor** (a paused one comes back only at 115% of it, through a probe): GCC answers one overuse by cutting to 0.85 of what arrived, and a screen's 1080p starting at its floor paused at the first one (its opening keyframe) until the next probe.
  - **Our pacer**, not pion's (one queue for everything, the voice behind keyframes): the voice goes out the moment it's written, video at 1.2× what the layers were given (not GCC's estimate, which climbs). RTX retransmissions find their stream's writer.
  - **The low-latency rate control isn't used for the room's layers.** Squeezed (a 360p layer at 255 kbps) it drops to 17–20 fps, and given its bitrate back in steps it stays there; the ordinary real-time rate control held 30 fps through the same swings (`TestBitrateSwings`) and encodes in 9.2 ms instead of 8.5 (`video-probe`, 720p, median), with a better worst PSNR (46.1 dB against 31.7).
  - **Dynacast, on huddle's SFU only** (step 4a). The SFU tells a publisher which layers anyone is sent (`signal.Wanted`: each viewer's layer, and the one its forwarder sends until a switch completes), at once when that grows and 3 s after a layer leaves it; for the first 10 s after a publish every layer is wanted, so the allocator has run every layer the uplink carries (the top one comes after a 4 s probe). A layer nobody wants is given nothing (`macvideo.Sender` then skips its encoder, and starts it again with a keyframe, the time skipped taken out of what VideoToolbox sees: `Encoder.Skipped`), and isn't a failed try. Wanted again, it comes back at its floor at once if it ran at its floor or more before, GCC's estimate leaves 1.15× its floor, and the estimate hasn't dropped since it paused; else it waits for a probe, as a layer the estimate paused does. Meanwhile the next smaller layer stands in for it (on the SFU, the nearest running layer stands in for its viewers), so a viewer is never left with nothing; with nothing running to carry a probe, the lowest layer needed starts at its floor. Through LiveKit Dynacast isn't followed: lksdk only sets a flag on the track that `WriteSample` ignores, so every layer is sent within the estimate.
- **Receiving.** Packets are put back together into access units by `room`'s assembler, not pion's samplebuilder, which holds each frame until the next frame's first packet comes (a frame's time; on a still screen share, until something changes). A unit also ends where the next one begins without its marker, at a new timestamp or a keyframe's first packet (the one carrying the SPS): an SFU cuts a frame off when it switches a viewer to another layer at that layer's keyframe, and the cut frame is dropped, not glued to the keyframe. The assembler starts at a keyframe's first packet (else after the first marker); it used to wait for the first marker, which threw away the keyframe a subscription starts with. Frames are shown only when newer than the last shown (RTP time, wrap-aware; more than 5 s behind is a clock that started over): a switch to a layer that lags sends a few frames again from its keyframe, decoded but not shown. A missing packet is waited for 250 ms from when it showed (a later packet came; lksdk's NACKs usually bring it back); after that the units it touched are dropped (to the next keyframe's first packet, or the packet after the next marker, whichever comes first), and the track waits for a keyframe and asks for one at once (a PLI through the subscriber connection: huddle doesn't use lksdk's single-connection mode, where `WritePLI` does nothing), again every 300 ms while no packet of one has come. Meanwhile a frame a packet shows isn't a keyframe is dropped at once, holes and all, so the keyframe goes out as soon as it's whole. The wait used to start when the assembler got to the hole: holes never mended then queued one 250 ms wait behind another, and at 20% loss with jitter the video fell 12–23 s behind (step 3b). Through LiveKit, a PLI stops its retransmissions until it forwards a keyframe (`FlagStopRTXOnPLI`): falling behind, the receiver asked about once a second, and 8.5% of packets were never mended; keeping up, 0.9%. A track shown again after `SetSize(0, 0)` waits for a keyframe and asks for one 100 ms after turning on. The first frame comes 70–200 ms after subscribing, at whatever layer the SFU sends first (step 1a's runs through LiveKit). It took about 1.1 s at the top layer (0.6 s at 180p) while the assembler waited for the first marker: that threw away the keyframe the SFU starts a subscription with, and the next came only after a PLI.
- **Lip sync.** A video frame is held until the same person's voice, as playout plays it (`jitter.Buffer.Playing`, plus the speaker's delay), reaches the time it was taken, for at most 500 ms. The two are compared by arrivals: each track keeps when each RTP timestamp would have come with the least delay of the last 2–4 s (`srClock`), and a person's voice and video cross the same network, so that least delay is the same for both. Sender reports are used only while a track has no packets: through LiveKit they come seconds in (frames led the voice by 40–55 ms until then), and a video's moves 1–13 ms from one report to the next, since pion stamps a report at the last packet written, after the encoder (LiveKit's down tracks send one every 3 s); the voice's agreed with its arrivals within a millisecond. LiveKit's made-up silent frames (f8 ff fe, then zeros; their timestamps run slow) don't count. Both clocks place a voice timestamp a packet (20 ms) late, a packet going out once all of it is captured, and the hold takes that off (`voiceSent`); a video's timestamp, its capture time, is placed late only by its encoding, about what Opus's own delay puts the sound behind. The voice's position comes only from pulls of the stream itself: through DTX silence a jitter buffer's position stands still, and holding against it made frames late by up to 110 ms. With no voice playing (none sent, or no speakers), frames show as they decode.
- **Camera and share in the app.** `setCamera(true)` asks for the Camera permission if macOS hasn't yet (only from the button), opens the camera picked in the menu (`devicePrefs.Camera`, else the default; asked again while on, it moves to the one picked), waits for its first picture to size the layers, and publishes; the self-view is the camera's own frames (`Mirror` set; the window mirrors your tile either way), and what's sent isn't mirrored. `setShare(true)` shows the system picker (on the main thread, through `performSelectorOnMainThread:`), returns once the share runs (nil when the picker was closed), and the share ends by itself from the menu bar's stop. - **VideoToolbox works through purego.** The output callbacks are made once and shared, keyed by an id in the refcon (purego never frees callbacks). The encoder's callback takes only scalars. The decoder's gets two CMTimes after the image; on arm64 a 24-byte struct arrives as a pointer to a copy, and purego callbacks take no structs, so they're `uintptr`s. Calls that take a CMTime by value (`VTCompressionSessionEncodeFrame`) go through `RegisterLibFunc`, which passes it by pointer as the ABI wants.
- **`huddle video-probe` at 720p30, 1.7 Mbps, paced in real time** (2026-10-28, this Mac):
  - **Frames:** 150 in, 150 out, none dropped, every barcode read in order.
  - **Keyframes:** at 0, 60 (every 2 s) and 90 (asked for at 90: the very next frame).
  - **Bitrate:** 1689 kbps.
  - **Speed:** encoding takes 8.5 ms per frame (median, from handing it over to the access unit coming out; 44 ms for the first frame); decoding takes 1.2 ms.
  - **PSNR:** brightness median 48.5 dB. Frames 15–17 dip to 29–32 dB: the 1-second data-rate limit (1.5× the average) makes the half-second after the first keyframe pay for it.
  - **Scaling:** 720p to 360p through `Scaler` takes 1.1 ms.
- **The encoder scales a frame of another size by itself.** A 720p buffer handed to a 360p encoder comes out 360p and reads right, so every simulcast layer's encoder can take the full-size capture buffer. Track P measured that against `Scaler`: cheaper (Track P's numbers, above).
- **A decoder given a stream that changes size makes its session again.** 720p, then 360p, then 720p takes 2 rebuilds, and every picture reads right. `VTDecompressionSessionCanAcceptFormatDescription` says no to a new size.
- **Low-latency rate control is offered here** (`kVTVideoEncoderSpecification_EnableLowLatencyRateControl`), with Constrained Baseline. Where it isn't, the encoder is made without it. Where there's no H.264 encoder at all (a CI virtual machine), the tests skip.
- **Loading VideoToolbox prints an AVCaptureDevice deprecation warning** about Continuity Cameras on stderr. It comes from the frameworks, not from us; nothing opens a camera.
- **How tiles draw (Track U).** Each frame the scene takes every video on screen from its source (`Take`: the newest frame if it's newer than the last taken, one copy under the track's lock) and puts it to the renderer (`PutFrame`); `Prepare` uploads the planes and runs `nv12.frag` into that video's RGBA texture (a camera cropped to 16:9, a share whole, your camera mirrored), and the tile draws it with `draw.List.Image` and its rounded corners. Each track hears the pixel size it's shown at when that changes (`SetSize`), and 0, 0 once it's off screen (a share not on stage, a camera behind the "+N" tile). A goroutine looks at the videos on screen every 4 ms (a `Take` with nothing to do) and wakes the loop when one has a new frame, so a call with no video still renders nothing while idle. Tiles appear once anyone's camera is on: a column on the right, or a row along the top when the stage would be narrower than 560; everyone but the whiteboard gets one, initials while their camera is off.
- **`tiles-bench`, six 360p tiles** (2026-10-28, this Mac, three runs of 600 frames): the main thread's part (take, put, upload, convert, submit) median 0.53–0.75 ms a frame, p90 0.63–1.12 ms, single frames up to 17 ms; the GPU's part 0.75–0.89 ms median. Six 720p tiles: median 2.2 ms, p90 3.6 ms. The GPU's pictures match `Frame.RGBA` at 47.6 dB (whole, mirrored) and 53.4 dB (cropped from 4:3); the largest differences are at colour edges, where the GPU interpolates the half-size colour plane and the CPU doesn't.

## The ears
A spoken command passes through more than a typed one: the person's track is decoded at 16 kHz; `pcm.Detector` finds each utterance (−45 dBFS, 60 ms of loudness to start, 450 ms of quiet to end, checked every 100 ms whether packets come or not); the utterance (with 300 ms before it) goes to that person's `gemini-3.5-transcribe-live` session, then `audioStreamEnd`; the final comes back; the gate waits 700 ms for more (`ContinueMs`) or, for the key, for the transcript of what was said while held. Measured through the app's mic path: last word → command about 0.9–1.0 s, then the brain's first op about 0.4–0.7 s. A typed command skips all of it.
- **The transcriber's final is usually 0.3–0.5 s after the stream end, and now and then seconds late.** A session sent the next utterance meanwhile folds both into one final (the user's first voice run: a minute of speech in one segment). So `transcribe` takes no more audio until the last utterance's final has come; after 4 s (`finalWait`) the latest interim stands in and the session is replaced. An utterance whose interims had no words (a cough, a noise) gets no final, so it waits 1 s (`noWordsWait`).
- **The app's mic sends DTX: one packet every 400 ms in silence, none when muted.** The ears read with a 100 ms deadline and feed the detector quiet on each timeout, so the end of speech is found ~450 ms after the last word instead of at the next packet (780–840 ms before). The fixture bots send every packet, so `agent-check` doesn't exercise this; `commands.wav` through `huddle voice -in` does.

## What the models do (live-probe, 2026-10-27)
`make live-probe` (`huddled live-probe [-only brain|transcribe] [-auto-schedule]`) asks the real models; about $0.10 a run. Findings:
- **`gemini-3.8-live` takes commands either way, mid-session.** Ten commands alternating client content (`Session.SendTurn`) and realtime text (`SendText`) in one session all drew: first tool call 0.35–1.0 s after the send. Neither path broke tool calls after the other was used.
- **A whole turn's tool calls come first, in one message, then audio.** On a question the `speak` call arrives at 0.36–0.42 s and the first audio at 0.86–1.3 s, after `speak` is answered. So the agent knows a turn will be spoken before any audio arrives.
- **Answer `speak` `WHEN_IDLE`, never `SILENT`.** A `SILENT` answer to `speak` left the question unanswered, and the model said that answer aloud during a later, unrelated command.
- **Answer successful drawing calls `SILENT`.** Answered `WHEN_IDLE`, a drawing turn starts another generation per answer: one command repeated the same three `add_node` calls six times, and another spoke filler ("<no speech>{pause}"). Answered `SILENT`, every drawing command came as one batch with `turn-complete` at the same moment, and no audio. A rejected call, `get_board` and `speak` are answered `WHEN_IDLE`, so the model can fix the call, use the read or speak (a `get_board` then a `connect` came 0.37 s apart).
- **A turn is over at a `turn-complete` with no `WHEN_IDLE` answer outstanding.**
- **`gemini-3.5-transcribe-live` takes 16 kHz s16 PCM in 100 ms chunks and returns text** (setup: TEXT modality, input transcription on). Interim hypotheses (`interimInputTranscription`) come about every 0.5 s while someone talks; the final (`inputTranscription`, then `generation-complete`) comes 0.35–0.58 s after the speech ends when the client sends `audioStreamEnd` at its own VAD's end of speech, and 1.4 s after with the server's VAD alone. The final is punctuated ("Whiteboard, draw our release process: build, then test, then deploy."); "White board" came back as "Whiteboard", but a trailing name sometimes comes without its comma ("…on the board now whiteboard?"). The service aborts a session after about a minute without audio (close 1008, "The operation was aborted"), so the ears close a quiet person's session at 40 s and open another when they speak.
- **Resumption works, with one catch** (`live-probe -only resume`). The server sends one resumable handle per turn, as soon as the turn is taken in. A connection opened with it continues the conversation (it answered "Marmalade." for a code word given on the first connection). But resuming while the old connection is still open fails: close it first. The agent reconnects only between turns, so it closes, then dials.
- **No GoAway came in 33 minutes on one `gemini-3.8-live` connection** with context compression on, unlike the documented ten minutes. The reconnect loop stays (GoAway, a dropped connection), and `agent-check -reconnect-every 8m` replaces the connection on a schedule to exercise it.
